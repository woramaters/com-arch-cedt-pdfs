# Ch6: Pipelining

## 6.1 ภาพรวม

::: term
[Pipelining]{.abbr} [การประมวลผลแบบสายพาน]{.th}

- **คืออะไร:** แบ่งการทำงานของคำสั่งเป็น **stages** แล้ว**ให้หลายคำสั่งทำงานซ้อนกัน**คนละ stage ในเวลาเดียวกัน ("start a new task as soon as the resources are available") เหมือนสายพานประกอบรถยนต์
- **ทำหน้าที่:** **เพิ่ม throughput** (ทำคำสั่งเสร็จได้ใกล้เคียง 1 คำสั่งต่อ cycle) **โดยไม่ลด latency** ของแต่ละคำสั่ง
- **สัมพันธ์กับ:** ต่อยอดจาก multi-cycle (Ch5) เพราะ resource แต่ละ stage ว่างอยู่แล้ว ("Since resources are there! Why not pipeline?") และนำไปสู่ superscalar/VLIW (Ch7)
:::

::: ex
**Laundry** (Ann, Brian, Cathy, Dave) มี 4 ขั้นตอนคือ wash, dry, fold, stash ขั้นละ 30 นาที
- **Sequential:** 4 คน × 4 ขั้น × 0.5 h = **8 ชั่วโมง**
- **Pipelined:** **3.5 ชั่วโมง**
- **k loads (Pop quiz):** เวลาเติม pipe 4 × 0.5 + (k − 1) × 0.5 = **(k + 3)/2 ชั่วโมง**
:::

::: key
**Lessons learned:**
1. **Pipelining ไม่ปรับปรุง latency ของงานเดี่ยว** แต่ช่วย **throughput ของทั้ง workload**
2. หลายงานทำพร้อมกันบน **resource ต่างกัน**
3. **ความเร็วถูกจำกัดด้วย stage ที่ช้าที่สุด**
4. **Stage ยาวไม่เท่ากันทำให้ speedup ลดลง**
5. **เวลา fill (เติม) และ drain (ระบาย) pipeline ทำให้ speedup ลดลง**
:::

::: term
[Pipeline stage]{.abbr} [ขั้นตอนในสายพาน]{.th}

5 stages ของ load (แบบคลาสสิก):
- **IF (Ifetch):** อ่านคำสั่งจาก instruction memory
- **ID (Reg/Dec):** decode และอ่าน register
- **EX (Exec):** ALU คำนวณ (สำหรับ load คือคำนวณ address)
- **MEM:** อ่านหรือเขียน data memory
- **WB (Wr):** เขียนผลกลับ register file
:::

::: term
[Pipeline register]{.abbr} [รีจิสเตอร์คั่นระหว่างขั้น (IF/ID, ID/EX, EX/MEM, MEM/WB)]{.th}

- **คืออะไร:** register ระหว่าง stage ที่พักข้อมูลและ **control signals** ของคำสั่งที่อยู่ใน stage นั้น
- **ทำหน้าที่:** แยกคำสั่งในแต่ละ stage ไม่ให้ปนกัน
- **สัมพันธ์กับ:** **forwarding** ดึงข้อมูลจาก register เหล่านี้ และ register เหล่านี้มี **overhead** (setup, clk-to-Q) ทำให้ speedup ไม่ถึง k เท่าพอดี
:::

::: term
[Fill / Drain / Flush]{.abbr} [เติม / ระบาย / ล้าง pipeline]{.th}

- **Fill:** ช่วงเริ่มต้นที่คำสั่งแรกยังเดินไม่ครบทุก stage (k cycles แรก)
- **Drain:** ช่วงท้ายที่ไม่มีคำสั่งใหม่เข้ามา
- **Flush:** ทิ้งคำสั่งที่ fetch มาผิด (เช่นเมื่อทาย branch ผิด)
:::

## 6.2 Speedup ของ Pipeline

::: formula
Multi-cycle (ทุกคำสั่งใช้ k cycles): T = n × k × T<sub>c</sub>

Pipeline: T = (k + (n − 1)) × T<sub>c</sub> (k = จำนวน stage = fill cycles)

Speedup ≈ n·k / (k + n − 1) → k เมื่อ n ใหญ่
:::

::: ex
100 คำสั่ง:
- **Single cycle** 45 ns → **4500 ns**
- **Multi-cycle** 10 ns, CPI 4.6 → **4600 ns**
- **Ideal pipeline** 10 ns, fill 4 cycles → (4 + 99) × 10 = **1030 ns** (ถ้านับแบบ (100 + 4) × 10 จะได้ 1040 ns)
- → **pipeline เร็วที่สุด** ประมาณ **4.4 เท่า**ของ single cycle
:::

**การวาด pipeline diagram (สไลด์):** แรเงาครึ่ง**ขวา** = **อ่าน** และแรเงาครึ่ง**ซ้าย** = **เขียน** (register file **เขียนครึ่งแรกของ cycle และอ่านครึ่งหลัง** จึงอ่านค่าที่เพิ่งเขียนใน cycle เดียวกันได้)

| Cycle | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| I1 | IF | ID | EX | MEM | WB | | |
| I2 | | IF | ID | EX | MEM | WB | |
| I3 | | | IF | ID | EX | MEM | WB |

## 6.3 Hazards

::: term
[Hazard (pipeline)]{.abbr} [ภาวะขัดข้องของสายพาน]{.th}

- **คืออะไร:** สถานการณ์ที่ทำให้คำสั่งถัดไป**เข้า pipeline ตามจังหวะปกติไม่ได้** ("The world is not perfect")
- **มี 3 ชนิด:** structural, data และ control
- **วิธีแก้แบบง่ายที่สุดคือรอ (stall)** แต่เสีย performance → pipeline control ต้อง **detect** แล้ว **resolve** (หรือหาทางเลี่ยง)
:::

::: term
[Stall / Bubble / NOP]{.abbr} [การหยุดรอ / ฟองอากาศ / คำสั่งว่าง]{.th}

- **Stall:** หยุดคำสั่งไว้ที่ stage เดิม 1 cycle ขึ้นไป
- **Bubble:** ช่องว่างใน pipeline ที่เกิดจาก stall (stage นั้นไม่ทำอะไรใน cycle นั้น)
- **NOP (No OPeration):** คำสั่งที่ไม่ทำอะไร ซึ่ง **software** แทรกเพื่อเว้นระยะแทนการให้ hardware stall
:::

| Hazard | สาเหตุ | Laundry | Processor |
|---|---|---|---|
| **Structural** | **resource ไม่พอ** มีคำสั่งต้องใช้พร้อมกัน | washer กับ dryer เป็นเครื่องเดียวกัน หรือ folder ไปดูทีวี | **memory เดียวใช้ทั้ง IF และ MEM**, **2 คำสั่ง WB พร้อมกัน** (register file มี write port เดียว) |
| **Data** | **ต้องใช้ข้อมูลก่อนที่มันจะพร้อม** ("ข้อมูลอยู่ในอนาคต") | เสื้อกับกางเกงชุดเดียวกันซักคนละรอบ, ถุงเท้าข้างหนึ่งยังอยู่ในเครื่องซัก | `LW r2` แล้ว `ADD r4,r2,r5` |
| **Control** | **ยังไม่รู้ว่าคำสั่งถัดไปคืออะไร** | ต้องดูผลซักก่อนจึงรู้ว่าใส่ผงซักฟอกเท่าไร | **branch** |

### แก้ Structural Hazard

- **เพิ่ม resource** ("solve by money"): **แยก instruction cache กับ data cache** (Harvard-style) หรือซื้อเครื่องซักเพิ่ม
- **Redesign:** ถ้ามีคำสั่งยาว 3/4/5 cycles ปนกัน เช่น **LW (5) ตามด้วย ADD (4) จะ WB ใน cycle เดียวกัน**
  1. **Stall / insert bubble:** control ซับซ้อน และเสียโอกาส fetch ("no instruction is started in cycle 6")
  2. **ให้ R-type ใช้ 5 stages** (มี MEM ที่เป็น NOOP) → **ไม่มี hazard** แต่ R-type ช้าลง 1 cycle (**design trade-off**) และนี่คือเหตุผลที่ pipeline มาตรฐานให้ทุกคำสั่งผ่าน 5 stages

::: ex
**ทำไม SW, BEQ, JMP ปนกับ R-type แล้วไม่เกิด structural hazard:**
- **SW, BEQ และ JMP ไม่มี WB (ไม่เขียน register file)** จึงไม่แย่ง write port
- SW ใช้ data memory เฉพาะใน stage ของตัวเอง
- BEQ/JMP แก้ PC ตั้งแต่ stage ต้น ๆ
- → ไม่มี resource ใดถูกใช้ซ้ำใน cycle เดียวกัน
:::

### แก้ Data Hazard

::: term
[Forwarding / Bypassing]{.abbr} [การส่งข้อมูลลัด]{.th}

- **คืออะไร:** ส่งผลลัพธ์จาก **pipeline register (EX/MEM, MEM/WB)** ตรงเข้า input ของ ALU **โดยไม่ต้องรอ WB**
- **ทำงานอย่างไร:** ตรวจหา**คำสั่งก่อนหน้าที่ใกล้ที่สุด**ที่จะเขียน register ที่เราต้องการ แล้วเพิ่ม **MUX** ให้เลือกข้อมูลจาก pipeline register แทน register file ("data is there, just bypass")
- **ข้อจำกัด:** **แก้ load-use ไม่ได้ทั้งหมด** ("ต้องมีไทม์แมชชีน") เพราะ LW ได้ข้อมูลตอน**จบ MEM** แต่คำสั่งถัดไปต้องใช้ตอน**ต้น EX ใน cycle เดียวกัน** → **ต้อง stall 1 cycle**
- **Data Forwarding = Data Bypassing**
:::

::: term
[Load-use hazard]{.abbr} [hazard จากการใช้ค่าที่เพิ่ง load]{.th}

- **คืออะไร:** คำสั่ง LW ตามด้วยคำสั่งที่ใช้ register ที่ LW โหลด **ทันที**
- **ผล:** ถึงจะมี forwarding ก็ต้อง **stall 1 cycle** หรือ compiler ต้อง reschedule
- **ถ้าไม่มี forwarding:** ต้องรอจน WB (สไลด์: stall ADD 3 cycles หรือแทรก NOP 3 ตัว)
:::

::: term
[Delayed load / Compiler scheduling]{.abbr} [การจัดลำดับคำสั่งโดย compiler]{.th}

- **คืออะไร:** ให้ **software ช่วย** โดย **ย้ายคำสั่งที่ไม่เกี่ยวข้องมาคั่น**ระหว่าง LW กับคำสั่งที่ใช้ค่า ถ้าหาไม่ได้ให้แทรก **NOP**
- **ข้อควรระวัง:** การย้ายคำสั่ง**ต้องไม่สร้าง dependency ใหม่** (RAW/WAR/WAW)
:::

```
LW  $r2, 20($r1)          ; ไม่มี forwarding ต้องแทรก NOP 3 ตัว
NOP
NOP
NOP
AND $r4, $r2, $r5
```

### แก้ Control Hazard

ใน design นี้ branch รู้ผลใน cycle ที่ 3

| วิธี | ทำอย่างไร | ต้นทุน |
|---|---|---|
| **Stall** | รอจนรู้ผล branch | ช้าลง 2 cycles ทุก branch |
| **Branch prediction** | ทายว่า taken หรือ not taken แล้ว fetch ต่อไปเลย | ทายถูกไม่เสียเวลา ทายผิดเสียประมาณ 1 cycle (flush) |
| **Branch delay slot** | **นิยามใหม่ให้คำสั่งถัดจาก branch ทำงานเสมอ** | ต้องให้ compiler หาคำสั่งมาใส่ |

::: term
[Branch prediction]{.abbr} [การทำนายทิศทาง branch]{.th}

- **คืออะไร:** ทายผลของ branch ล่วงหน้าแล้วทำงานต่อไปเลย (**speculative execution**)
- **ความแม่นยำ:** **ทายแบบคงที่ยังถูกอย่างน้อยประมาณ 50%** ส่วน**แบบใช้ branch history ถูกประมาณ 90%**
- **ถ้าทายผิด:** ต้อง flush คำสั่งที่ทำไปตามทางผิด
:::

::: term
[Branch delay slot]{.abbr} [ช่องหน่วงหลัง branch]{.th}

- **คืออะไร:** ตำแหน่งคำสั่ง**ถัดจาก branch** ที่จะ **execute เสมอไม่ว่า branch จะ taken หรือไม่** (branch มีผลช้าไป 1 คำสั่ง)
- **ทำหน้าที่:** ใช้ช่วงเวลาที่ปกติจะเสียไปให้เกิดประโยชน์
- **เงื่อนไข:** **ต้องมี software/compiler ช่วย** หาคำสั่งที่ไม่เกี่ยวกับเงื่อนไขของ branch มาใส่ ถ้าไม่มีให้ใส่ NOP
:::

```
ไม่มี delay slot:              มี delay slot:
ADD $r1,$r2,$r3               BEQ $r2,$r3,BRANCH
BEQ $r2,$r3,BRANCH            ADD $r1,$r2,$r3     ; ทำเสมอ (ย้ายมาจากข้างบน)
ORI $r4,$r5,#100              ORI $r4,$r5,#100
```

::: trap
ย้าย ADD เข้า delay slot ได้เพราะ **BEQ ไม่ได้ใช้ `$r1`** ถ้า BEQ อ่าน `$r1` จะย้ายไม่ได้ (จะเกิด RAW)
:::

## 6.4 Data Hazard 3 แบบ (Part 2)

กำหนด j = คำสั่งก่อน และ i = คำสั่งหลัง; Rregs = register ที่อ่าน และ Wregs = register ที่เขียน

::: term
[RAW]{.abbr} [Read After Write]{.full} [อ่านหลังเขียน · true dependence]{.th}

- **เงื่อนไข:** r ∈ **Rregs(i) ∩ Wregs(j)** คือ i ต้อง**อ่าน**ค่าที่ j **เขียน** แต่ถ้า i อ่านเร็วเกินไปจะได้ค่าเก่า
- **ตัวอย่าง:** `a = 7; b = a + 5;`
- **แก้:** **forwarding แก้ได้เกือบทุกกรณี** (ยกเว้น load-use ที่ต้อง stall 1 cycle)
- **เป็น dependency จริง** (rename ไม่ได้)
:::

::: term
[WAW]{.abbr} [Write After Write]{.full} [เขียนหลังเขียน · output dependence]{.th}

- **เงื่อนไข:** r ∈ **Wregs(i) ∩ Wregs(j)** คือทั้งคู่เขียน register เดียวกัน แต่ถ้า i เขียนเสร็จ**ก่อน** j ค่าสุดท้ายจะผิด
- **ตัวอย่าง:** `a = data[1000]; a = 10; b = a + 3;` (load ช้าเพราะ memory)
- **แก้:** หลีกเลี่ยงด้วย design, software หรือ **out-of-order + register renaming**
:::

::: term
[WAR]{.abbr} [Write After Read]{.full} [เขียนหลังอ่าน · anti-dependence]{.th}

- **เงื่อนไข:** r ∈ **Wregs(i) ∩ Rregs(j)** คือ i เขียนทับก่อนที่ j จะอ่านค่าเดิม
- **ตัวอย่าง:** `a = sin(x); x = 10;` (sin ต้องเตรียมนาน จึงอ่าน x ช้า)
- **ความถี่:** **พบได้ยากใน architecture สมัยใหม่** และหลีกเลี่ยงได้ด้วย design
:::

::: key
- **ไม่มี RAR (Read After Read)** เพราะการอ่านไม่เปลี่ยนค่า อ่านลำดับไหนก็ได้ผลเท่ากัน
- **ใน in-order 5-stage pipeline** (อ่านใน ID และเขียนใน WB ตามลำดับเสมอ) **เกิดปัญหาจริงได้แค่ RAW**
- **WAR/WAW เป็นปัญหาเมื่อ** คำสั่งมี latency ต่างกัน หรือทำงานแบบ **out-of-order** (Ch7)
- **WAR และ WAW เป็น "name dependence"** แก้ได้ด้วย **register renaming** ส่วน RAW เป็น dependency จริง
:::

## 6.5 Pipelined Datapath, Hazard Detection, Forwarding

::: term
[Unified decoder]{.abbr} [ตัวถอดรหัสรวม]{.th}

- **คืออะไร:** decode คำสั่ง**ครั้งเดียวที่ ID** แล้ว**ส่ง control signals ไปพร้อมคำสั่ง**ผ่าน pipeline registers แต่ละ stage จะใช้เฉพาะสัญญาณของตัวเอง
- **ตัวอย่าง "Give it a try":** ใน cycle 7 แต่ละ stage ทำคนละคำสั่ง: Fetch 100, Dcd 34, Ex 30, Mem 24, WB 20
:::

::: term
[Hazard detection unit]{.abbr} [วงจรตรวจจับ hazard]{.th}

- **คืออะไร:** วงจรที่เก็บ **pending writes** (register ที่คำสั่งใน pipeline จะเขียน) แล้วเทียบกับ operand (rs, rt) ของคำสั่งที่กำลังจะ issue
- **ทำงานอย่างไร:** เมื่อคำสั่ง issue ให้ **reserve** register ปลายทาง และเมื่อเสร็จให้ลบ reservation
- **สมการ:** hazard = **((rs = rw_ex) AND regW_ex) OR ((rs = rw_mem) AND regW_mem) OR ((rs = rw_wb) AND regW_wb)** และเงื่อนไขเดียวกันกับ **rt**
- **สัมพันธ์กับ:** ใช้ **comparator** (Digital Logic) และสั่ง stall หรือเลือกทาง forwarding
:::

::: key
- **Memory operations:** ถ้าคำสั่งเริ่ม **in-order** และ memory op อยู่ stage เดียวกันเสมอ **จะไม่มี hazard ระหว่าง memory op ด้วยกัน**
- **Load ที่มี dependency** ใช้ **"Delayed loads"** (compiler scheduling)
- **Summary ของ pipelining:**
  - ใช้ resource คนละตัวในแต่ละ step
  - เริ่มคำสั่งถัดไปขณะที่คำสั่งปัจจุบันยังไม่เสร็จ
  - **ถูกจำกัดด้วย stage ที่ยาวที่สุด (บวก fill/flush)**
  - ต้อง **detect และ resolve hazards**
:::

## 6.6 Exercises Ch6

::: ex
**Data hazards ในสไลด์:**
```
MOV  R1, F0        ; ใช้เวลานาน (เขียน R1 ช้า)
LI   F0, #20
LD   R2, R1, 0
ADDI R1, R1, #1
```
- **WAR บน F0:** MOV อ่าน F0 แต่ LI เขียน F0 อาจเขียนก่อน MOV อ่านเสร็จ
- **RAW บน R1:** MOV → LD และ MOV → ADDI
- **WAW บน R1:** MOV กับ ADDI (ADDI อาจเขียนก่อน MOV)
- **WAR บน R1:** LD อ่าน R1 แต่ ADDI เขียน R1
:::

::: ex
**Rescheduling** (full forwarding + delayed load + delayed branch)
```
เดิม:                           Reschedule:
Loop: LD   F0,0(R1)             Loop: LD   F0,0(R1)
      ADD  F4,F0,F2                   LD   F1,8(R1)
      SD   0(R1),F4                   ADD  F4,F0,F2
      LD   F1,8(R1)                   ADD  F5,F1,F2
      ADD  F5,F1,F2                   SD   0(R1),F4
      SD   8(R1),F5                   SUB  R1,R1,#16
      SUB  R1,R1,#16                  BNEZ R1,Loop
      BNEZ R1,Loop                    SD   -8(R1),F5   ; อยู่ใน delay slot
```
- จุดสำคัญ: **SD ที่ย้ายไปไว้หลัง SUB ต้องปรับ offset จาก 8 เป็น 8 − 16 = −8** เพราะ R1 ถูกลด 16 ไปแล้ว
:::

# Ch7: Contemporary Architecture (ILP)

## 7.1 ภาพรวม

Pipeline ธรรมดาทำได้ดีที่สุด CPI = 1 บทนี้หาวิธีทำให้ **CPI < 1** (หลายคำสั่งต่อ cycle) หรือลด IC โดยอาศัย **parallelism** ทั้งจาก hardware (dynamic) และ compiler (static)

::: term
[Flynn's Taxonomy]{.abbr} [การจำแนกของ Flynn (Michael Flynn, 1966)]{.th}

- **คืออะไร:** จำแนกคอมพิวเตอร์ตามจำนวน **instruction stream** กับ **data stream**
:::

| | Single Data | Multiple Data |
|---|---|---|
| **Single Instruction** | **SISD**: uniprocessor | **SIMD**: **vector processor**, GPU |
| **Multiple Instruction** | **MISD**: **fault-tolerant computing** | **MIMD**: **multicore, distributed systems** |

::: term
[ILP]{.abbr} [Instruction-Level Parallelism]{.full} [ความขนานระดับคำสั่ง]{.th}

- **คืออะไร:** **จำนวนคำสั่งในโปรแกรมที่ execute พร้อมกันได้**
- **เทคนิค:** vectorization, **speculative execution** (รวม branch prediction), pipelining/superpipeline, **superscalar** (out-of-order execution, register renaming), **VLIW**
- **ข้อจำกัด:** dependency (data/control) และจำนวน resource
:::

::: term
[Speculative execution]{.abbr} [การทำงานล่วงหน้าแบบคาดเดา]{.th}

- **คืออะไร:** execute คำสั่ง (หรือบางส่วน) **ก่อนที่จะรู้แน่ว่าต้องทำ** เช่นทำตามทางที่ branch prediction ทายไว้
- **ถ้าทายผิด:** ทิ้งผลลัพธ์ทั้งหมด
- **ทำหน้าที่:** เลี่ยงการ stall จาก control dependency
:::

## 7.2 Vector Processor (SIMD)

::: term
[Vector processor / SIMD unit]{.abbr} [Single Instruction, Multiple Data]{.full} [หน่วยประมวลผลเวกเตอร์]{.th}

- **คืออะไร:** **ทำ operation เดียวกันกับข้อมูลหลายตัว (vector/array) ในคำสั่งเดียว**
- **ตัวอย่าง:** **Altivec** (Apple/Motorola/IBM), **Intel MMX, SSE2/3/4, AVX/AVX2/AVX-512**, GPU (CUDA, OpenCL)
- **ในสไลด์:** gcc `-O3` vectorize `C[i] = A[i] + B[i]` เป็น `paddd` ซึ่งบวก int 4 ตัวพร้อมกัน และ vector processor บางแบบ expand loop ภายในเอง
- **เปรียบเทียบ:** สั่ง "**บะหมี่ 10 ถ้วย**" ครั้งเดียว พ่อครัวรับ order ครั้งเดียวแล้วทำทั้งหมด
:::

## 7.3 Superscalar, Superpipeline, VLIW

ตัวแปรที่ใช้: k = จำนวน stage, n = จำนวนคำสั่ง, x = degree (issue width), m = minor cycles ต่อ major cycle, T<sub>c</sub> = major cycle

::: term
[Superscalar]{.abbr} [ซูเปอร์สเกลาร์]{.th}

- **คืออะไร:** มี **pipeline หลายชุด (degree x)** และ **hardware แจกคำสั่งเข้า pipeline แบบ dynamic** ทำให้ issue ได้ x คำสั่งต่อ cycle
- **ILP:** k·x (เช่น degree 2 × 5 stages = 10 คำสั่ง in flight)
- **เวลา:** **T(n) = (k + (n − x)/x) T<sub>c</sub>** → speedup เทียบ pipeline ≈ **x**
- **เปรียบเทียบ:** ร้านอาหารมี**แถวเดียว** แล้ว**ผู้จัดการแยกลูกค้า**ไปแถวข้าวกับแถวบะหมี่
- **ผลข้างเคียง:** อาจเกิด **out-of-order execution** (คนสั่งบะหมี่ที่มาทีหลังได้ก่อนคนสั่งข้าว) → เสี่ยง **WAR และ WAW** แก้ด้วย **in-order completion** หรือ **register renaming**
- **ลดอะไร:** **ลด CPI** (CPI = 1/x)
:::

::: term
[Out-of-order execution (OoO)]{.abbr} [การทำงานไม่ตามลำดับ]{.th}

- **คืออะไร:** hardware execute คำสั่งที่ **operand พร้อมแล้ว** ก่อน โดยไม่ต้องรอคำสั่งก่อนหน้าที่ยังรอข้อมูล
- **ทำหน้าที่:** ซ่อน latency และใช้ resource ให้เต็มที่ (**dynamic scheduling**)
- **ปัญหา:** WAR/WAW → ต้องใช้ register renaming และ in-order completion (commit ตามลำดับ)
:::

::: term
[Register renaming]{.abbr} [การเปลี่ยนชื่อรีจิสเตอร์]{.th}

- **คืออะไร:** ให้คำสั่งที่เขียน register ชื่อเดียวกัน**ใช้ physical register คนละตัว**
- **ทำหน้าที่:** **กำจัด WAR และ WAW** (name dependence) ทำให้แต่ละ iteration ของ loop เป็นอิสระต่อกัน
- **ทำได้ทั้ง:** hardware (superscalar) และ compiler (ตอน loop unroll)
:::

::: term
[Superpipeline]{.abbr} [ซูเปอร์ไปป์ไลน์]{.th}

- **คืออะไร:** แบ่ง major cycle เป็น **m minor cycles** แล้ว**เริ่มคำสั่งใหม่ทุก minor cycle** (pipeline ที่ลึกและเร็วขึ้น)
- **ILP:** m·k
- **เวลา:** **T(n) = (k + (n − 1)/m) T<sub>c</sub>** → speedup ≈ **m**
- **Superpipelined superscalar:** ILP = m·k·x และ T(n) = (k + (n − x)/(m·x)) T<sub>c</sub>
:::

::: term
[VLIW]{.abbr} [Very Long Instruction Word]{.full} [คำสั่งยาวพิเศษ]{.th}

- **คืออะไร:** **compiler** จับหลาย operation ที่อิสระต่อกันมา**รวมไว้ใน 1 คำสั่งยาว** (x operations ต่อ word) แล้ว hardware ก็ execute ทั้ง word พร้อมกัน
- **Scheduling:** **static** (ทำตอน compile)
- **ILP:** k·x
- **เวลา:** **T(n) = (k + (n/x − x)) T<sub>c</sub>** (ตามสไลด์) → speedup ≈ **x**
- **ลดอะไร:** **ลด IC** (n → n/x) โดย CPI = 1
- **เปรียบเทียบ:** ร้านอาหารมี **2 แถวแยกตั้งแต่แรก** (แถวข้าวกับแถวบะหมี่) โดยลูกค้าต้องรู้เองว่าต้องเข้าแถวไหน
- **ปัญหา:** **binary ไม่ compatible ข้ามรุ่น** เพราะ schedule ผูกกับ hardware (Itanium → Itanium II), Intel ประกาศ **EOL ของ Itanium ใน ม.ค. 2019**, ส่วน Transmeta Crusoe ก็ไม่ได้รับความนิยม
:::

::: key
**SuperSymmetry: ที่ degree เท่ากัน superscalar, superpipeline และ VLIW ให้ performance เท่ากัน** (n ใหญ่ → speedup = x, m, x ตามลำดับ)

| Architecture | IC | CPI | T<sub>c</sub> | Potential speedup |
|---|---|---|---|---|
| Single cycle | n | 1 | L | 1 |
| Multi-cycle | n | 3–5 (avg 4.2) | L/5 | 1.xx |
| Pipeline | n | 1 | L/5 | 5 |
| Superscalar (degree k) | n | **1/k** | L/5 | 5k |
| Superpipeline (m) | n | **1/m** | L/5 | 5m |
| VLIW (x per word) | **n/x** | 1 | L/5 | 5x |
:::

::: ex
**ใช้ 2 pipelines (Int + FP) พร้อมกัน**
- loop รวมใช้ 19 cycles โดย Int ใช้ 7 และ FP ใช้ 12 (fmult 7 + fadd 5)
- CPU time = max(Int, FP) → speedup = 19/12 ≈ **1.6**
:::

## 7.4 Compiler & ILP

::: term
[Loop unrolling]{.abbr} [การคลี่ลูป]{.th}

- **คืออะไร:** **คัดลอกตัว loop หลายรอบไว้ใน iteration เดียว** แล้วลดจำนวนรอบลง (เช่น i −= 4)
- **ทำหน้าที่:**
  - ทำให้ **basic block ใหญ่ขึ้น** จึงมีคำสั่งอิสระมาเติม slot หรือคั่นระหว่าง load กับ use ได้
  - ลด overhead ของ loop (SUB/BNE)
- **ต้องทำร่วมกับ:** **register renaming** ให้แต่ละ iteration ใช้ register ต่างกัน
- **ข้อเสีย:** **code ใหญ่ขึ้น** และ**จำนวน register จำกัดจำนวนรอบที่ unroll ได้**
:::

::: ex
**`A[i] = A[i] + C`**
- **Loop ปกติ:** LW, (stall), ADD, (stall), (stall), SW, SUB, BNE = **8 cycles/iteration**
- **Unroll 4 รอบ + reschedule + renaming:** **14 cycles / 4 iterations = 3.5 cycles/iter** → speedup = 8/3.5 ≈ **2.29**
- **Unroll 5 รอบ + superscalar (Int + FP):** **12 cycles / 5 iter = 2.4 cycles/iter** → speedup ≈ 3.33
:::

::: term
[Software pipelining]{.abbr} [การทำ pipeline ด้วยซอฟต์แวร์]{.th}

- **คืออะไร:** จัด loop ใหม่ให้แต่ละรอบ**ทำงานคนละขั้นของคนละ iteration** (เช่น SW ของ i, ADD ของ i+1, LW ของ i+2)
- **ส่วนประกอบ:** **start-up** code ก่อน loop และ **clean-up** code หลัง loop
- **ข้อดี:** **"unroll เท่าที่จำเป็น"** ได้ **performance ดีและ code ไม่ใหญ่มาก**
:::

::: term
[Dynamic vs Static scheduling]{.abbr} [จัดลำดับโดย hardware vs โดย compiler]{.th}

- **Dynamic (hardware, OoO superscalar):** hardware unroll loop และ issue หลายคำสั่งแบบ dynamic
- **Static (software/compiler, VLIW):** compiler unroll และ schedule หลายคำสั่งต่อ cycle
:::

| | **Dynamic** | **Static** |
|---|---|---|
| ใครจัดลำดับ | hardware ตอนรัน | compiler ตอน compile |
| Legacy software | **เร็วขึ้นบน HW ใหม่โดยไม่ต้อง recompile** | ต้อง recompile (**poor compatibility**) |
| Hardware | **ซับซ้อน ใช้ power สูงกว่า** | **ง่าย ใช้ power ต่ำกว่า** |
| ข้อมูลที่ใช้ | รู้ dependency จริงตอนรัน (เช่น cache miss) | เห็น scope กว้างกว่า แต่ **dependency บางอย่างรู้ไม่ได้ตอน compile** (pointer alias) |

::: key
**ใครชนะ:** สไลด์สรุปว่า dynamic ทำให้ legacy software ได้ประโยชน์ ส่วน static จะดีกว่าถ้า compiler เก่งพอ แต่ "**proven to be too difficult to have good compiler**" → **ในทางปฏิบัติ dynamic (OoO superscalar) ชนะ**
:::

## 7.5 Multicore และ Thread-Level Parallelism

::: term
[Multicore]{.abbr} [ชิปหลายแกน]{.th}

- **คืออะไร:** หลาย **core** (แต่ละ core เป็น superscalar) อยู่ในชิปเดียว หรือมองเป็น "multiple pipes"
- **ประเภท:** MIMD
- **สัมพันธ์กับ:** **Amdahl's Law** (ส่วน serial จำกัด speedup)
:::

::: term
[TLP / SMT]{.abbr} [Thread-Level Parallelism / Simultaneous MultiThreading]{.full}

- **TLP:** ความขนานระดับ thread
- **SMT:** เมื่อ thread เดียวเติม slot ของ processor ไม่เต็ม ก็**ดึงคำสั่งจากหลาย thread** เข้า pipeline พร้อมกัน
- **Intel เรียก SMT ว่า Hyper-Threading Technology**
:::

::: ex
**Dynamic superscalar degree 2 (OoO)** จากตารางในสไลด์:
- `LW f0` issue 1, EX 2, MEM 3, WB 4
- `ADD f2,f0,f1` issue 1 แต่**รอ f0** จึง EX 5–7 และ WB 8
- `SW f2` issue 2 และ**รอ f2** จึง MEM 9
- `SUB r1` issue 2, EX 4, WB 5 → **เสร็จก่อน ADD (out-of-order)**
- `BNE` issue 3, EX 6
- iteration ถัดไปเริ่ม issue ที่ cycle 4 ซ้อนกับรอบแรก
:::
