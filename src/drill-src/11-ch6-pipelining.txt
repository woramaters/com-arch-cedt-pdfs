%TITLE Ch6: Pipelining และ Hazards
%CODE L
%REVIEW
- **Pipelining** เพิ่ม **throughput** ไม่ลด latency · ความเร็วถูกจำกัดด้วย **stage ที่ช้าที่สุด** · stage ไม่สมดุลและเวลา fill/drain ลด speedup
- **T = (k + n − 1) × T<sub>c</sub>** → speedup ≈ k · laundry 4 ขั้น × 30 นาที: k loads = (k + 3)/2 ชั่วโมง
- **5 stages:** IF → ID (Reg/Dec) → EX → MEM → WB · register file เขียนครึ่งแรกอ่านครึ่งหลังของ cycle
- **Structural** (resource ไม่พอ: memory เดียว, WB พร้อมกัน) → เพิ่ม resource (แยก I/D cache), stall/bubble หรือ redesign (ให้ R-type ใช้ 5 stages)
- **Data:** RAW = Rregs(i) ∩ Wregs(j) (forwarding แก้ได้เกือบหมด) · WAW = Wregs(i) ∩ Wregs(j) · WAR = Wregs(i) ∩ Rregs(j) · ไม่มี RAR · in-order 5-stage มีปัญหาจริงแค่ RAW
- **Load-use:** ต้อง stall 1 cycle แม้มี forwarding (ถ้าไม่มี forwarding ต้องรอ 3) → compiler reschedule (delayed load) หรือแทรก NOP
- **Control:** stall (2 cycles), branch prediction (≥ 50%, history ~90%), **branch delay slot** (คำสั่งหลัง branch ทำเสมอ ต้องให้ compiler ช่วย)
- **Hazard detection:** เทียบ rs/rt กับ register ปลายทางที่รอเขียนใน EX/MEM/WB
%ENDREVIEW

%SA
5-stage pipeline (full forwarding) cycle time 2 ns รัน 200 คำสั่ง โดย 10% เป็น load-use และไม่มี stall อื่น ใช้เวลาเท่าใด
=224 cycles = 448 ns
5 + 199 + 20 = 224 (CPI ที่มีผล ≈ 1.12)
%SA
โปรแกรม 7 คำสั่งของ nanoLADA (LW, LW, ADD, ORI, SW, BEQ, JMP) จงหาเวลาบน single cycle 230 ns, multi-cycle 50 ns และ ideal pipeline 5 stages 50 ns
=single 1610 ns, multi 1400 ns (28 cycles), pipeline 550 ns
pipeline = (5 + 7 − 1) × 50 → เร็วกว่า single 2.93 เท่า (ไม่ถึง 5 เพราะ n น้อย)
%SA
ระบุ dependency ทั้งหมดและจำนวน stall (full forwarding): `1: LW r1,0(r2)` · `2: ADD r3,r1,r1` · `3: SW r3,4(r2)` · `4: ADD r1,r4,r5`
=RAW r1 (1→2), RAW r3 (2→3), WAR r1 (2→4), WAW r1 (1→4) · stall 1 cycle
เฉพาะ load-use (1→2) ที่ต้อง stall ส่วน WAR/WAW ไม่เป็นปัญหาใน in-order 5-stage → รวม 9 cycles
%SA
`1: LW r1,0(r2)` · `2: ADD r3,r1,r4` · `3: LW r6,4(r2)` · `4: SUB r7,r6,r3` · `5: ORI r8,r9,#5` (full forwarding) ใช้กี่ cycle และจะ reschedule ให้ไม่มี stall ได้อย่างไร
=11 cycles → reschedule: LW r1; LW r6; ADD r3; ORI r8; SUB r7 = 9 cycles
- dependency: RAW r1 (1→2), RAW r6 (3→4), RAW r3 (2→4) ไม่มี WAR/WAW
- load-use 2 จุด จุดละ 1 stall → 9 + 2 = 11
- reschedule แล้วไม่สร้าง dependency ใหม่
%SA
`1: LW r2,0(r1)` · `2: ADD r3,r2,r4` · `3: SUB r2,r5,r6` · `4: SW r3,4(r1)` ทำไมย้าย SUB มาคั่นระหว่าง 1 กับ 2 เพื่อลด stall ไม่ได้ และต้องทำอย่างไร
=ละเมิด WAR (2→3) และ WAW (1→3) บน r2 → ต้อง rename ปลายทางของ SUB (เช่น r7) ก่อนจึงจะย้ายได้
ถ้าย้ายตรง ๆ ADD จะอ่าน r2 ของ SUB แทนค่าที่ load มา
%SA
(Exercise ในสไลด์) `MOV R1,F0` (ช้า) · `LI F0,#20` · `LD R2,R1,0` · `ADDI R1,R1,#1` มี hazard อะไรบ้าง
=WAR F0 (MOV/LI), RAW R1 (MOV→LD, MOV→ADDI), WAW R1 (MOV/ADDI), WAR R1 (LD/ADDI)
MOV ใช้เวลานาน คำสั่งหลังจึงอาจเขียนก่อนที่ MOV จะอ่านหรือเขียนเสร็จ

(Exercise ในสไลด์) reschedule loop นี้ให้ไม่มี stall โดยใช้ delayed load และ delayed branch: `LD F0,0(R1); ADD F4,F0,F2; SD 0(R1),F4; LD F1,8(R1); ADD F5,F1,F2; SD 8(R1),F5; SUB R1,R1,#16; BNEZ R1,Loop`
=LD F0; LD F1; ADD F4; ADD F5; SD 0(R1),F4; SUB R1,R1,#16; BNEZ; SD −8(R1),F5 (อยู่ใน delay slot)
SD ตัวสุดท้ายย้ายมาหลัง SUB จึงต้องปรับ offset จาก 8 เป็น 8 − 16 = −8
